# DSH Security-Tool Ecosystem — Inventory & Gap List (2026-09)

**Audit date:** 2026-09-11
**Scope:** security-relevant tooling in / around the DeepSeek Harness (DSH) plugin ecosystem, as of September 2026.
**Baseline audited for overlap:** `@moonquake2004/dsh-security` **v0.1.7** — `src/checks/index.mjs` (22 built-in checks: sp1–sp10, sr1–sr4, sl1–sl4, ss1–ss4) and `src/integrations/*` (4 external integrations: poison-guard, sandbox-audit, plugin-reducer, ecosystem).
**Method:** read-only. `gh search repos` (repo + topic probes), `gh api repos/*` for metadata, `gh api graphql` discussion search on `deepseek-ai/deepseek-harness`, `npm view` / registry API / PyPI JSON for publication and activity, and **direct reading of READMEs, `package.json` manifests, CLI entrypoints and report-shape source** for every tool characterised below. Nothing was posted to GitHub; no third-party tool was installed or executed; no repository file was modified except this report.

**Companion document:** `docs/threat-survey-2026-09.md` (same day) covers the *threat* landscape (discussion reports, platform vulnerabilities, candidate *offline checks*). This document covers the *tooling* landscape — what exists, how it is invoked, whether it is alive, and which pieces are worth wiring into `src/integrations/`.

**Scope note on the ecosystem size.** The `dsh-plugin` GitHub topic carried **14,371 repos** at audit time (`gh api search/repositories -q 'topic:dsh-plugin'` → `total_count`), of which **170** match a further `security` term and **21** match `scanner`. The inventory below is therefore a *curated* set of the security-relevant survivors found via ~30 repo/npm/topic/discussion probes — not an exhaustive census. Anything named in the task brief but not verified is in **Unverified**.

## 0. How to read this inventory

Two axes matter for us:

* **Invokable tool** — has a `bin`, runs from a shell, can emit machine-readable output. These are candidate `src/integrations/` targets.
* **Framework plugin** — a Cordis/`dsh.bundle.patch` package with **no `bin`**. It works only when installed into a profile and loaded by the host; it exposes tools/hooks to the model. Not invokable by us from `execFileSync`, so it can never satisfy our integration contract.

Our current integration contract (as implemented in `src/integrations/*.mjs`) is:

```
isAvailable()  → execFileSync('which', [bin])                     # PATH probe
run(target)    → execFileSync(bin, [target, '--json'])            # or [cmd, target, '--json']
                 → JSON.parse(stdout) → { id, ok, severity, detail, fix? }
```

Activity is reported from the npm publish timestamp and/or the last GitHub push. "Stale" below means no publish/push since **2026-08-20** and no release since then.

## 3. Gaps

### (a) Threat classes covered by other tools that we do not cover

Cross-referencing the 22 built-in checks (naming/secrets/injection in patch files, npm+OSV vulns, dist-tags, dual-instance core leak, client-bundle syntax, sandbox-config consistency, session-log escape/priv-esc/exfil/credential/PII scans) against the characterisations above:

| # | Uncovered threat class | Who covers it today | Why it matters | Rank |
|---|---|---|---|---|
| G1 | **Prompt injection in untrusted *content*** — including **homoglyph / zero-width / full-width obfuscation** of an injection payload | `dsh-secure-audit` (`security_scan_text`, ruleset v4), `dsh-mcpguard` (skills + MCP configs), `bigclawd/dsh-security-guard`, `GavinTomlins` scanner | The #3051/#6019 SSRF + indirect-injection path and #4514 make fetched content the primary delivery vector. Our checks look at *files on disk*, not *content that arrives at runtime*. Nothing we ship normalises Unicode confusables. | **1** |
| G2 | **Install-time lifecycle-script execution surface + tarball verification** | `dsh-vet` (`dep.install-scripts`), `npm-safe --deep`, `dshpkg` (lifecycle + hardened extraction), `dsh-poison-guard` (install-script rules) | #2961/#5498: install hooks run *before* any post-install scanner can look, and a tarball need not match the repo. Our sp1 is `npm audit`-shaped; nothing flags `preinstall`/`postinstall`/`prepare` or verifies published bytes. | **2** |
| G3 | **Dependency-graph hygiene beyond CVEs** — peer-range resolvability, broken `latest`, floating/non-registry sources, missing licenses, staleness, installed-vs-declared drift | `dsh-dep-audit` (8 checks), `dsh-vet` (`dep.floating-range`, `dep.typosquat-proximity`), `dsh-audit` (npm signal), `dsh-plugin-doctor` (R7 rescope-`cordis`, peer-rc residue) | sp8 catches one dist-tag brokenness class and sl2 catches version regression; we do **not** check peer resolvability or drift — the ERESOLVE class that #2763 and the ecosystem tracker keep producing. | **3** |
| G4 | **Cordis-contract / boot-smoke verification of an installed bundle** | `dsh-plugin-doctor` (R+K offline, D online) — exit codes make it a real CI gate | #1863's matching lint shipped in this tool, and K-group catches inject-vs-access and `ctx.effect` violations that are invisible to us. ### (d) Supply-chain observations worth recording (not integrations)

* **Namespace squatting.** `omdsh-dev/dsh-security-audit` sets `"name": "@deepseek-ai/dsh-security-audit"` in a **private** package — i.e. a third-party repository publishes *under the official DeepSeek scope name*, and it is not on npm. Anyone reading a report, screenshot, or profile manifest sees what looks like an official package. This is the same class of confusion #3395 documented for marketplace names (`dsh-plugin-marketplace` ×5 etc.). We should not treat `@deepseek-ai/*` as a trust signal without checking the source of the manifest — and our `sp9`/sp-family checks should keep that in mind. *(Source: `package.json` read directly from the repo.)*
* **Dangling repository URLs.** `dsh-security-gate@0.1.3` and `dsh-security-tools@0.1.2` both declare `repository → github.com/ihuajiu/dsh-code-security`, which **404s**; `dsh-security-tools` additionally claims to wrap `@openai/codex-security`. Both are on npm with a combined ~250+ downloads/mo and no readable source. Treat as unauditable.
* **Name collisions inside our own integration surface.** Three different projects answer to "dsh-plugin-doctor" (`@perrylink/dsh-plugin-doctor` on npm; the bare npm name `dsh-plugin-doctor` = `Xrainsmile/DSH-Plugin-Doctor`; and `zoahdev/dsh-plugin-doctor` GitHub-only). The PerryLink README explicitly warns never to run `npx dsh-plugin-doctor`. Any integration must use the **scoped, version-pinned** name.

## 4. Recommended integrations

Ordered, with the contract mapping each one needs.

1. **`dsh-vet` → EXT-VET-1** (severity HIGH, phase POST_INSTALL).
   `dsh-vet --json <target>` → read `summary` for `ok`/severity, map `findings[].severity` (`critical|high|medium|low|info`) and gate on `confidence ∈ {medium, high}` exactly as the contract requires (low-confidence findings must not fail). Populate `fix` from `findings[].remediation`/`title` and reference `docs/rules/<id>.md`. Skip when the binary is absent. Pin the npm version in docs; note the 0.3.0-vs-0.4.0 gap.
   *Covers G2, G3, G5, G8.*

2. **`@perrylink/dsh-plugin-doctor` → EXT-DOC-1** (severity MEDIUM, phase POST_INSTALL; static-only by default).
   `dsh-plugin-doctor --repo <profileDir> --no-smoke --only R,K --json -`. Read `results[].name` prefixes plus the documented exit codes; treat **exit 6 as `skip`, not pass** — that is the whole point of the contract. Scoped name only.
   *Covers G4.*

3. **`dsh-dep-audit` → EXT-DEP-1** (severity HIGH, phase LIFECYCLE).
   `dsh-dep-audit <profileDir> --json`. Map `checks[].status` `fail`→fail, `warn`→report-only, and honour `--offline` when the profile is offline so we do not turn a network failure into a false pass.
   *Covers G3.*

4. **Fix or retire the two broken integrations** (this is higher value than any new addition):
   * `sandbox-audit.mjs` — rewrite to invoke per-YAML-file (`<profileDir>/cordis.patch.yml` + each bundle's declared `dsh.bundle.patch`) and read `findings[].title`/`severity`; or, since the binary is unpublishable, **delete the integration** and fold its three HIGH/MEDIUM rule families into `sp3` (which already covers the same ground statically and offline).
   * `plugin-reducer.mjs` — switch to `--dsh-home <dshHome> --profile <name> --probe <kind> --json`, read `report.result.minimalFailingSet`, drop the hard-coded `/tmp`, and replace `which` with a cross-platform probe.
   * `poison-guard.mjs` — read `{verdict, findings[]}` instead of `{clean, vulnerabilities}`; `verdict === 'CLEAN'` → ok.
   * `ecosystem.mjs` — add a staleness guard on the newest weekly/release-compat file.

5. **(Conditional) `npm-safe` via `@npm-safe/core` → EXT-NPM-1**, only if we decide npm-package tarball verification (`--deep`) belongs in our remit; otherwise cite it in docs as the recommended companion for the install-time gap (G2) that we deliberately do not close ourselves. `dshpkg` stays a documented alternative rather than an integration until it leaves 0.1.0 and has a second release.

**Do not integrate** (framework plugins — no `bin`, cannot satisfy the contract): `dsh-secure-audit`, `dsh-security-guard`, `dsh-mcpguard`, `dsh-plugin-vetting`, `dsh-guardwall`, `secret-guard`, `dsh-guardrails`, `@deepseek-ai/dsh-security-audit`, `dsh-audit`, all `dsh-guardian` forks, and `hol-guard`. For these the right move is a **documentation pointer** — the same pattern the ecosystem already uses ("complements dsh-poison-guard and dsh-plugin-doctor") — so users know what to install for the runtime/pre-install half we do not cover.

## 5. Unverified

Everything below was **not** verified to the standard used above. Do not cite it as fact.

* **`dsh-security-gate` and `dsh-security-tools` (publisher `ihuajiu`)** — declared repository `github.com/ihuajiu/dsh-code-security` returns **404**. I read only the npm metadata. What they actually do, and whether the advertised `@openai/codex-security` wrapping is real, is unverified.
* **`@deepseek-ai/dsh-security-audit` (omdsh-dev)** — I read `package.json` and README only; I did not read its `src/` and did not confirm that the claimed redaction/path-fencing properties hold in code. Its **94.7%-style capability claims are its own**, not measured here. Its `private: true` + official-scope name is verified (manifest read directly); *intent* is not — I make no assertion of malice.
* **`dshpkg`** — the README claims "hardened extraction (traversal/symlink/bomb guards)" and "stdlib-only"; I read the README and PyPI metadata, not the parser. Its A–F grades are uncalibrated by any third party I found. One release, 0.1.0.
* **`hol-guard` / `plugin-scanner`** — README + PyPI metadata only. I did not read the scanner or confirm the `plugin-scanner scan` JSON output shape (the README shows `scan`/`lint`/`verify` without a documented `--json` contract), so its contract fit is *assumed from the family*, not verified.
* **`dsh-audit-trail` / `auditrail`** — npm metadata shows a `bin`, but I did not read the CLI; its argument surface and JSON output are unverified.
* **AgentGuard study (#5636) and `agentguard-research`** — the 94.7% High/Critical figure is a **capability-surface** rating from a sample the authors chose; neither the methodology nor the dataset was independently audited here. `docs/threat-survey-2026-09.md` §5 already flags this. Do not cite it as vulnerability prevalence.
* **`dsh-security-evaluation-dataset`** — I listed its top-level entries only; whether its `cases/` are usable as fixtures (labels, licensing, size) is unverified. No license declared.
* **Framework plugins in §1b** — characterised from **README descriptions only** (no source read) except where a `package.json` is cited: `bigclawd/dsh-security-guard`, `dsh-security-scanner`, SecurityGate, `dsh-plugin-trustlens`, `dsh-security-doctor`, `dsh-guardrail`, `dsh-guardrails`, `dsh-guard-sensitive-paths`, `dsh-guardian`, `secret-guard`, all `dsh-guardian` forks. Their rule counts, hook names and behaviour are the authors' claims.
* **`dsh-mcpguard`'s "public poisoning corpus"** — referenced in discussion #3059 as 25 synthetic samples with no executable payloads (per the threat survey). I did not open it.
* **Existence/quality of tools named in the task brief that I did not find or verify:** `dsh-sandbox-audit` as an *npm package* does not exist; `dsh-ecosystem` exists only as a GitHub repo. I found no evidence for any other external integration the brief might imply.
* **`dsh-plugin-reducer` npm `latest` vs `v0.3.1`** — the README asserts the GitHub release tarball is the real 0.3.1 artifact and that npm's `latest` is a bootstrap tag. I verified the README text, the GitHub tag, and the npm `dist-tags`; I did **not** verify the OIDC/provenance attestation or diff the two artifacts.
* **Completeness.** The `dsh-plugin` topic carried 14,371 repos and `dsh-plugin security` 170. My ~30 probes surfaced roughly 60 security-relevant projects, of which this report characterises ~45. High-star niche tools with no security wording in their description would not have been found. Treat the inventory as a curated sample, not a census.
