# DSH Plugin Ecosystem — Threat Survey & Candidate Checks

**Survey date:** 2026-09-11
**Scope:** reported security threats and incidents in and around the DeepSeek Harness (DSH) plugin ecosystem, roughly June–September 2026.
**Method:** read-only GitHub GraphQL discussion search on `deepseek-ai/deepseek-harness` (probe terms: malicious plugin, poison, supply chain, credential leak, api key, sandbox escape, permission, approval, prompt injection, typosquat, npm token, secret, 恶意, 投毒, 泄露, plus CVE/GHSA, backdoor, compromised, provenance, signing, exfiltration, scanner). Bodies and comments fetched for ~50 discussions. `gh search repos` / `gh search code` for ecosystem scanners. No repository files were modified except this report; nothing was posted to GitHub.
**Baseline audited for overlap:** `dsh-security` v0.1.7, `src/checks/index.mjs` + all 22 check modules and `src/integrations/*`.

**Headline finding (strict):** as of 2026-09-11 there is **no confirmed, in-the-wild malicious DSH plugin incident** reported anywhere in the official discussions. The ecosystem's own trust projects say so explicitly: the dshlib census comment on #3395 reports 305 plugins reviewed by third parties (232 pass / 73 flagged for human review, *“无确认恶意”* — no confirmed malicious), and the AgentGuard study (#5636) states its 94.7% High/Critical rating *“does not mean that 94.7% of plugins are malicious or contain confirmed vulnerabilities.”* What **does** exist is a large body of independently reproduced **harness vulnerabilities that a malicious or compromised plugin can exploit** (in-process load-time code execution, unauthenticated local control plane, approval-bypass ordering), plus capability surveys and several confirmed **scanner false positives**. Any check we add must therefore target *mechanisms*, not a malware signature database — there is no ground-truth corpus to validate signatures against.

## 3. Candidate checks (ranked, max 5)

All five are static, zero-dependency, and need only files under `$DSH_HOME/profiles/<profile>/` plus resolved config; none executes plugin code.

### C1 — Patch-layer security-row override (proposed `sp11`)
**Threat:** #587 (bundle patch rewrites approval/sandbox at boot), #4094 (last-write-wins whole-row replacement, no protected rows, no warning), #454 (`!!js` + patch layers as the load-time attack surface).
**Inspects:** profile `package.json` → `dsh.profile.bundles` (layer order); each bundle's `package.json` → `dsh.bundle.patch`; the resolved patch YAML of every layer; the profile's own `cordis.patch.yml`; and `--dump-config` output when the CLI is available (read-only invocation is already how sp8 probes config).
**Detects:** any layer that sets/overrides a row id matching a security vocabulary (`sandbox*`, `approval*`, `permission*`, `credentials*`, `*-policy`) when the effect is a **weakening** — `mode: danger-full-access`, approval `policy: never`, `disabled: true`, preset downgrade, or credentials-provider substitution — and names the layer that won. Ignores additive non-security rows.
**Offline:** yes — all YAML/JSON on disk.
**FP risk:** **medium**. Legitimate plugins do tune sandbox rows. Mitigations: fail only on weakening (never on additions), name the layer + old→new value, and support an explicit allowlist in `~/.dsh/security.json` (config plumbing already exists in `registry.setConfig`). If a base snapshot is unavailable, degrade to `warn`.
**Severity:** `error` (critical when sandbox policy or approval is disabled/downgraded).

### C2 — `!!js` config-as-code tag and bundle-patch path sanity (proposed `sp12`)
**Threat:** #454 (live-verified `!!js` = host RCE at load), #587 (load-time `!!js` executes before guards), #3354 (`dsh.bundle.patch` path traversal, `!!js` evaluated on boot).
**Inspects:** every patch layer reachable from the profile and from each bundle's declared `dsh.bundle.patch`; flag (a) the `!!js` tag/scalar in any *third-party* layer, (b) a `dsh.bundle.patch` value that is absolute or contains `..` segments, (c) a bundle patch path that resolves outside its package directory.
**Offline:** yes.
**FP risk:** **low**. The official `@deepseek-ai/*` base ships no `!!js`, and the profile's own user patch legitimately uses it (e.g. `port: !!js ctx.webStartup.port ?? 3080`, seen in #1919). Exempt the user patch's non-privileged uses; still `warn` if a user-patch `!!js` expression references `child_process`, `fs` write APIs, `process.env`, or credentials.
**Severity:** `error` for `!!js` in a third-party bundle/plugin layer or an escaping patch path; `warn` for exempted user-patch cases.
**Overlap note:** sp4's regex may incidentally match `eval(`/`Function(`/`child_process` text inside a patch, but it does not flag the `!!js` tag, does not model layer provenance, and does not check paths. This is a refinement, not a duplicate.

### C3 — Code Mode × restrictive sandbox mismatch (proposed `sp13`)
**Threat:** #3245 (Critical, independently verified twice): `run_code` bypasses the file-effect sandbox entirely, so `DSH_TOOLS_MODE=code|both` + default `read-only`/`workspace-write` = full host file/process authority.
**Inspects:** resolved tools mode (`DSH_TOOLS_MODE`, and code-runtime rows in the composed config) against the resolved sandbox policy / permission preset, reusing sp3's config-resolution approach.
**Detects:** tools mode in `{code, both}` **and** code runtime = worker-thread **and** sandbox mode in `{read-only, workspace-write}` → fail with the remediation options from #3245 (switch to `native`, use `danger-full-access` knowingly, or mount a confinable runtime). `danger-full-access` passes (nothing to escape).
**Offline:** yes — pure config.
**FP risk:** **low**, provided an unknown mode/policy yields `skip` rather than a guess.
**Severity:** `error` (the report scores it 9.8–10.0; a silent escape from the default policy is not a warning).

### C4 — Plugin bundle tamper/drift baseline (proposed `sl5`)
**Threat:** #454 — “post-install tampering loads with zero checks” and “`dsh plugin remove` does not remove a persisted `!!js` backdoor”; #587 — persistence at boot. sl1 compares the **lockfile** against the registry, so it does *not* notice `node_modules` bytes changed after install.
**Inspects:** content hashes of each installed third-party plugin's load-bearing files (`package.json`, `dsh.bundle.patch` target, entry points, patch YAML), stored in a baseline under `$DSH_HOME` (same pattern dsh-plugin-vetting already uses with `baseline.json`); on subsequent runs, re-hash and report drift, plus a diff of the declared `dsh.bundle.patch` target.
**Detects:** files changed after first observation, new/moved entry points, a patch target that changed since install, and — combined with C2 — a `!!js` payload that was added post-install.
**Offline:** yes (local hashing + a local baseline file; first run records and passes).
**FP risk:** **low–medium**. Legitimate edits (dev `link:` installs, HMR, self-updating plugins) will drift; key on the install source (skip `file:`/`link:` symlinked packages) and report drift as informational on the first change, escalating when the changed file contains a newly-added `!!js`/exec/network pattern.
**Severity:** `warn` on drift; `error` when drift adds executable config or a security-bearing row change.

### C5 — Install-time execution surface & source pinning (proposed `sp14`)
**Threat:** #454/#587 (a malicious bundle executes in the host process at install/load), #2961/#5498 (tarball need not match the repo; install hooks run before any post-install scanner; SLSA/provenance can attest a poisoned pipeline), #5815 (silent wrong-package install with exit 0), #5636 (32 plugins with `AUTO_UPDATE`).
**Inspects:** each installed plugin's `package.json`: `scripts` keys `preinstall|install|postinstall|prepare|prepublishOnly`; native-addon markers (`gypfile`, `binding.gyp`, `*.node`) in a third-party package; and provenance/pinning in the profile — dependency specs that are floating (`latest`, `*`, `^`, `~`, `github:` without a commit sha), plus a **dependency-key vs installed `name`/`version` mismatch** (the direct symptom of #5815).
**Detects:** “this plugin runs arbitrary code on your machine at install time,” and “what you asked to install is not what landed.”
**Offline:** yes for all of the above (lockfile + `node_modules` + manifests). Deliberately **excludes** tarball-vs-repository diffing, which needs the network.
**FP risk:** **medium–high** — many legitimate plugins use `prepare` to compile TS. Mitigate: `warn` for a lifecycle script alone; `error` only for lifecycle script **plus** a floating source, a name mismatch, or a `curl|wget`-to-exec payload; exempt `@deepseek-ai/*` (with the content-hash caveat from #1663).
**Severity:** `warn` by default; `error` for the escalated combinations.

### Also considered (offline-detectable, ranked out of the top 5)

* **Hook side effects before approval** (#1863) — scan installed plugin source for `tools/pre-execute` / `agent/pre-step` / `approval/request` listeners co-located with `child_process`/fs-write/fetch. Fully offline; FP medium (same-file matching) and prior art exists in dsh-plugin-doctor v1.9.0. Strong candidate for a sixth slot.
* **MCP bridge approval gap** (#3904) — detect configured MCP servers and grep the installed `dsh-mcp-client` lib for the approval seam (empty → warn), plus unpinned/remote server commands. Offline; FP medium because it is version-sensitive.
* **`AUTO_UPDATE` remote-fetch-then-execute** (#5636, 32 plugins) — a natural sp10 extension. FP medium; recommended after C5.
* **Credentials at rest / `.env` precedence** (#4039, #3503, #1559, #952) — check `$DSH_HOME/.credentials.yaml` perms (0600) and plaintext, project-`.env` vs user-env precedence for `DEEPSEEK_API_KEY`, and whether a non-official `baseURL` is configured. Offline, low FP; overlaps sp2 but checks different failure modes.

## 4. Rejected candidates (cannot be verified offline)

| Rejected candidate | Source reports | Why it cannot be an offline check |
|---|---|---|
| Tarball-vs-repository artifact diff (published files that never existed upstream) | #2961, #5498, #454 (“post-install tampering”), #5081 | Requires downloading the repo at the anchored commit **and** the npm tarball. Offline we can only compare against a locally captured baseline (that is C4, which detects *post-install* change, not install-time mismatch). sl1 already does the network-dependent lock-vs-registry integrity check. |
| SLSA provenance / Sigstore Rekor transparency-log verification | #5498, #5081, #2961 | Needs Rekor/OCI/registry network access; the whole value is the external log. A local-only version would verify a self-signed manifest against itself and prove nothing. |
| “Confirmed malicious plugin” signature/blocklist | #2312, #3059, #4616, #5636 | No wild samples exist (#3395 comment: *no confirmed malicious*; #3059's corpus is explicitly synthetic, no executable payloads). Building signatures from synthetic fixtures guarantees either useless coverage or high FP; it would also require shipping/updating a corpus, violating the zero-dependency constraint. |
| Live sandbox-escape confirmations (bwrap remount, WSL2 interop, Windows ACL/DeleteFile, `<drive>:\tmp`, explorer.exe elevation) | #1769, #3045, #4688, #5871, #2562, #3032, #3252 | Confirmation requires *attempting* an OS-level escape on the host; file inspection cannot establish it. The only offline facts are uninformative preconditions (OS = Windows, sandbox = workspace-write), which would fire constantly — unacceptable FP. (The *config-level* Code-Mode mismatch, which is decidable offline, is C3.) |
| Pre-install prompt-injection detector for fetched web content / third-party relay responses | #3051, #5226, #2549, #4514 | The payload is remote and unbounded; you cannot decide offline whether an arbitrary fetched page or relay response contains an injection. Only post-hoc session-log detection is possible, and sr3/ss1/ss3 already cover credential-forwarding and exfil patterns there. A “third-party baseURL configured” warning is a trust/disclosure note, not a detector. |
| Reputation / download-count / maintainer-health scoring | #5636, #3395, sl3 | Needs npm/registry APIs; sl3 already does the online variant and correctly returns `skip` when offline. |
| Runtime telemetry hot-reload poisoning detection (G-3) | #454 | The poisoning happens through a live hot reload to an attacker endpoint; offline you can only detect that a telemetry exporter URL is present and non-official (a weak, disclosure-grade signal), not that a flip occurred. Better handled as a config warning than a check. |

## 5. Unverified

* **#2756** — “deepseek-harness存在安全漏洞导致我的apikey泄露” (overnight quota use with no chat usage). No root cause established; comments speculate about third-party balance-check plugins/middlemen or an unauthenticated `dsh web` on a shared host. **Unverified.**
* **#5226** — auto-generated sessions uploading files/keys to `tflink`. The reporter's screenshots and account are credible, and the community diagnosis (a third-party relay/中转站 injecting “run a one-shot dsh CLI command, don't tell me the result,” then `curl`-uploading config) fits the source facts, but it was **not independently reproduced** by a maintainer. Treat as unverified-but-plausible; the post-hoc signature (`curl`/`Invoke-WebRequest` upload from a shell tool) is already in sr3's reach. Key rotation was advised, not confirmed done.
* **#5636** — the AgentGuard 94.7% High/Critical figure is a **capability** rating from an external X article and dataset; the methodology and CSV were not independently audited here. Do not cite it as a vulnerability prevalence number.
* **#454** — G-1 (project instruction/skill injection) and G-3 (telemetry hot-reload poisoning) are author-live-verified but I found **no independent reproduction** in-thread; the `!!js`/install-exec/tamper findings were the ones other reporters corroborated or restated.
* **#3252** — three containment mechanisms read from source; the author explicitly states they were **not executed** end-to-end.
* **Fix status is version-specific and unresolved:** #5815 was still present at `0.1.3-alpha.1`; #3245 had only a fork fail-closed branch at survey time; #1220/#853 hardening is disputed in #6093. No maintainer security advisory or CVE was found for any plugin-malware event; `#6093` (CVE-2026-82533) is an argument *against* a CVE, not a plugin advisory.
* **No private disclosure channel:** #1220, #1932 and #3252 all note `SECURITY.md` is absent, private vulnerability reporting is disabled, and Issues are disabled — so the reports above are necessarily public and some (#3252) are deliberately incomplete. Our threat picture is therefore bounded by what people were willing to post publicly.
